## 一、任务与交付物

用户需要**一份文档**：对标行业四足机器狗，给出逐步开发路线，并标注本仓已完成/未完成；同时给出本周相对重要的落地项（用户特别询问「重力补偿是不是相对挺重要的」）。

已确认口径（本轮澄清）：

1. **只交付路线图文档**，本周不改代码、不落地 RQ-025。
2. 形式：**Markdown**，落到 `docs/trotbot/开发路线.md`，与现有需求/架构文档并列。
3. 对标范围：**全栈 L0-L5**（含感知/导航作为延伸层说明），但**本仓只评估到运动控制层**。

- 新增 `docs/trotbot/开发路线.md`（唯一实质交付物）

### 2.3 关键结论（用于回答「重力补偿是否重要」）

- 当前是 **MIT 位置控制 + 50Hz 轨迹**：机体自重完全靠 `kp·(q_des−q)` 的位置误差承担，导致静态下塌、跟踪误差、kp 偏大→发热/振荡。
- 已实现 **静态查表重力前馈**（RQ-022，实测 12 维，默认关闭），但只在标定姿态附近有效，姿态变化后失配。
- 未实现 **随位形变化的模型重力前馈**（RQ-025）——这是从「能动」到「走得稳、可继续加动态步态」性价比最高的一步，且是后续 WBC/MPC 的前置基础。
- 但顺序上应先做**量化基线**（用 `motor_monitor_node` 记录关节误差/力矩）+ **符号与增益阶梯验证**，否则重力补偿可能反而放大偏差。

## 三、文档结构与内容规划（`docs/trotbot/开发路线.md`）

### §0 文档定位
- 与 `软件需求清单.md`（RQ 条目）、`架构说明.md`（实现）、`开发问题跟踪.md`（问题）的分工；路线图只回答「往哪走、走到哪、下一步做什么」。
- 状态图例：✅ 已完成 / 🟡 部分完成 / ⬜ 未开始；每条状态附代码或文档依据。

### §1 行业对标：四足能力分层 L0-L5
- 定义每层的**能力目标 + 可验收标志**：
  - L0 硬件与通信底座｜L1 关节级控制与标定｜L2 整机安全与启停编排｜L3 基础运动与步态｜L4 状态估计与地形适应｜L5 动力学与高级运动
  - 延伸层 L6+：感知/导航/自主/交互（明确「不在本仓当前范围」）
- 对标对象与差异（定性，不写易失真的具体参数）：
  - 消费级：Unitree Go2、小米 CyberDog 2、云深处 Lite3
  - 工业级：Boston Dynamics Spot、云深处 X30
  - 各层「行业标配做法」一列，便于看出本仓差距在算法/传感器/集成，而非电机与通信。

### §2 本仓现状看板（一页）
- 按 L0-L5 的完成度表（✅/🟡/⬜ + 一句话证据），数据来自本计划 §2.1/§2.2。
- 明确「已闭环的链路」：`CHAMP → MIT → CAN → 电机反馈 → RViz`、上/下电状态机、零位一次性初始化、灯语。

### §3 逐层路线（每层固定小节）
每层写：目标能力 → 行业做法 → 本仓现状 → 差距与风险 → **验收要点（DoD）** → 依赖（硬件/人力）。
重点展开：
- L2 安全：补 `safety_manager`、Fault 闭环、失联降级（对应 RQ-020）。
- L3 步态：步态参数体系化、walk 慢速步态、步态切换。
- L4 状态估计：IMU 接入（`has_imu`）、姿态融合、足端接触；地形适应。
- L5 动力学：静态前馈 → 模型重力前馈（RQ-025）→ 摩擦/惯量辨识 → WBC/MPC。

### §4 分阶段路线图（时间只写阶段，不写人天）
- **M0 已完成**：L0-L2 底座 + L3 基础 trot。
- **M1 本周**：见 §5。
- **M2 近期**：L2 安全加固、L4 IMU 接态估计、L3 步态参数化。
- **M3 中期**：L4 地形适应、L5 摩擦/惯量辨识。
- **M4 远期**：WBC/MPC、动态步态、感知导航（延伸层）。

### §5 本周优先事项（3 项，按 ROI 排序）
1. **重力补偿闭环（最高优先）**：先量化基线（`motor_monitor_node` 记录站立/慢走的关节误差与力矩）→ 开启 RQ-022 静态前馈（`gravity_ff_scale` 0.2→0.5）做 A/B → 记录结论；为 RQ-025 模型前馈准备好符号与增益口径。
   - 写清「为什么重要」：位置控制下重力由位置误差承担；补偿可降误差/降 kp/降发热，是后续动态步态的地基。
   - 写清「风险」：符号反了会加重下塌；必须逐关节验证、小增益起步、可一键关闭。
2. **站立/慢走稳定性基线**：固定测试场景与记录表（关节误差、机体高度、温度、电流），作为后续一切改动的对照。
3. **安全兜底最小项**：软件急停/失联降级的需求条目化（不在本周写代码，但列出 DoD 与影响面），避免后续加动力学时缺少安全网。
- 每项给：目标、动作、验收、阻塞依赖（如 IMU 硬件是否到位）。

### §6 风险与依赖
- 硬件：IMU 是否有、电池监控、足端传感；机械间隙/标定精度。
- 算法：定基重力模型在 roll/pitch 下的误差；符号标定工作量。
- 组织：单人联调窗口、实机安全工装。

### §7 附录
- RQ 编号与路线图层级映射表（RQ-001～025 → L0-L5）。
- 术语表（MIT、RNE、WBC、MPC、tau_ff、zero_sta 等）。

### §8 维护约定
- 状态变更时同步 `软件需求清单.md` 对应 RQ 与本文 §2 看板；新增能力先补需求条目再进路线。

## 四、关键决策与假设

| 项 | 决策 |
|---|---|
| 分层方式 | 自定 L0-L5（硬件→关节→安全→步态→状态估计→动力学），L6+ 为延伸层 |
| 对标写法 | 只写**能力维度**与行业做法，不写具体速度/负载等易失真参数；需要数字时标注「以公开规格为准」 |
| 状态判定 | 以本仓代码与 `declare_parameter` 为准，不采信旧文档口径；有冲突以代码为准并在文档注明 |
| 本周项 | 只写「做什么+怎么验收」，不写工期；重力补偿排第一并给出理由与风险 |
| 是否改代码 | **否**。不新建节点、不改 launch/YAML，只写文档 + 导航一行 |
| 与 RQ-025 计划的关系 | 文档引用其结论（定基、仅重力项、默认关闭、`replace/add`），但不复制实现细节，避免两份文档漂移 |
